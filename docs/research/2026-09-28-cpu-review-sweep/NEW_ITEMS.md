**golden_run.py verify must fail when a number turns NaN or an infinity changes**

- **status:** proposed (review sweep 2026-09-28; verifier status of its findings: confirmed)
- **priority / type / role:** P1 / infra / implementer
- **area:** scripts/golden_run.py, tests/
- **growth point and timing:** MVP growth point 1; land it before the first module move of NT-026, NT-027 or NT-028, and before any golden record that later items verify against.
- **why:** D-023 makes `scripts/golden_run.py verify` the 'no number changed' check for every module move (NT-026 (8), NT-027 (5), NT-028 (7), NT-042 (3), NT-046 (5), NT-049 (4)). The comparison at golden_run.py:95-101 zeroes the difference only where BOTH sides are NaN (`both_nan`). Where only one side is NaN, `diff` is NaN, and `np.nanmax(diff - tol)` then ignores it. If a whole array becomes NaN, nanmax returns NaN, and `NaN > 0` is False. Either way the key counts as passed, and `ok = not bad and not missing` (line 110) returns exit code 0 with {"golden_equal": true}. So a refactor that makes a loss, a metric, a learned period or a prediction non-finite passes the guard. It also passes when a NaN in the recording turns into a finite value. Merged findings: [TOOL-1](findings/static-tools-sweep.md#tool-1) (scripts/golden_run.py verify reports 'golden_equal: true' when outputs turn NaN or an inf becomes finite).

(2) The test imports no TensorFlow and runs in under 5 s. (3) The printed summary names each NaN-mismatch key as FAIL. (4) ruff passes. Also from [TOOL-1](findings/static-tools-sweep.md#tool-1): (1) tests/test_golden_run.py, with run() monkeypatched: verify exits 1 for one element NaN on one side only, a whole array NaN, a NaN loss history, inf -> finite and +inf -> -inf. ### CPU-04

**Temperature scaling reaches the NLL minimum (bounded scalar search instead of fixed-step gradient descent)**

- **status:** proposed (review sweep 2026-09-28; verifier status of its findings: confirmed)
- **priority / type / role:** P1 / bug / implementer
- **area:** src/neural_trade/calibration/temperature_scaling.py, calibration/pipeline.py (summary label), tests/
- **growth point and timing:** MVP growth point 2; land it before NT-030's first sweep and before the R2 studies read calibrated P(up).
- **why:** _fit_temperature (temperature_scaling.py:62-106) fits T with 500 steps of plain gradient descent from T=1, with lr=0.05. The gradient is dNLL/dT = mean((p-y)(-z/T^2)), which scales with the logit variance and with 1/T^2. For small logits, or for any T far above 1, the total movement 500*0.05*|grad| is far too small to reach the optimum. The loop has no convergence test and no upper bound. The best-T bookkeeping is also one step off: nll is computed on base_logits/T_old (line 91, used at line 102), but best_T stores T_new (lines 99-104). This project's direction heads have P(up) s.d. of about 0.02-0.03 (runs/experiments/direction_v1/REPORT.md:52), so the logit s.d. is about 0.1. In that regime the fitted T stays in [0.86, 1.05] whatever the true temperature is, from 0.33 to 17. Every gate run's temperatures are in [0.94, 1.03]: m3 1.012/0.991/0.951, m4 0.997/0.998/0.981, m5 1.024/0.940/1.013, m6 1.009/0.985/1.033 (runs/gates/m*/analytics.json 'temperature'). These are consistent with an optimiser that barely moves, not with heads that are well calibrated. Calibrated P(up) is the served p_up_calibrated. It feeds SignalFrame (the agreement and consensus votes at 0.55/0.45), threshold_spike (0.45/0.55), enhanced_multi_horizon and liberal. It is also used for calibrated ECE/Brier and for the reliability diagrams. The context of D-009 ('fixed 0.55/0.45 lines are rarely crossed by calibrated P(up)') rests on these probabilities. AUC and MCC at 0.5 are unaffected, because T > 0 keeps the order and the sign of the logits. Merged findings: [FUZZ-1](findings/property-fuzz-sweep.md#fuzz-1) (Temperature scaling never reaches the NLL minimum: fixed-step gradient descent stalls near T = 1 on weak heads, so the 'calibrated' P(up) is barely calibrated).

**The gross book of the backtest does not depend on the cost setting**

- **why:** Each position is sized from net equity: notional = size_frac x equity_cash (backtest.py:208). equity_gross adds that position's P&L to gross_cash and uses the same net-sized unrealised P&L (backtest.py:189-191, 255-257). Here it shrank the gross figure by 12-40%. It feeds the 'gross vs net' diagnostics in STATUS.md:26 (+2.3% gross) and NT-005's 'gross +4.1% (the same as buy-and-hold)'.
