## DATA-1: The training shuffle does not shuffle: a 2048-element buffer over 30,213 chronological windows makes every epoch walk forward in time, and loss-weight calibration only sees the oldest 17% of the training block

- **Severity:** P2 (reported P1). **Status:** confirmed. **Type:** bug. **CPU cost:** instant. **Placement:** new item CPU-18.
- **Files:** `src/neural_trade/data/datasets.py`, `src/neural_trade/training/lambda_calibration.py`, `src/neural_trade/training/trainer.py`

**Description.** create_datasets (datasets.py:21) builds the training set with ds.shuffle(buffer_size=2048, seed=seed, reshuffle_each_iteration=True). The input is the fold -1 train block in chronological order (30,213 sequences on the bundled CSV). A shuffle buffer this small only mixes nearby elements. Each epoch therefore runs almost in time order: the first batches come from 11-13 Oct and the last from about 27 Oct to 1 Nov. SGD/Adam steps are not i.i.d., and the weights at the end of each epoch (the state that EarlyStopping, ReduceLROnPlateau and the checkpoint judge on val) are tilted toward the newest days. calibrate_loss_weights (lambda_calibration.py:43, 102, 115) takes train_ds.take(n_warmup) and train_ds.take(n_sample). With CALIB_SAMPLE_FRACTION 0.1 that is 12 batches, and they cover only sequences 0..5001: 2025-10-11 03:29 to 2025-10-14 14:50, just after the 10 Oct crash. Every run with calibrate=True (the default for train, gate_run and the notebooks) therefore sets its 13 loss weights from an unrepresentative, more volatile slice. The comment at datasets.py:19-20 shows that shuffling was intended. The buffer size dates from the initial commit (34d4599).

**Failure scenario.** Default config, fold -1, bundled CSV: one epoch of train_ds gives corr(batch number, mean chronological index) = 0.9989. ## DATA-2: sort_dedupe uses an unstable sort, so 'keep the last row of duplicated timestamps' keeps an arbitrary duplicate

- **Severity:** P2. **Status:** confirmed. **Type:** bug. **CPU cost:** instant. **Placement:** addition to NT-041.
- **Files:** `src/neural_trade/data/preprocessors.py`, `tests/registries/test_data_registries.py`

**Description.** sort_dedupe (preprocessors.py:36-38) runs df.sort_values('timestamp').drop_duplicates(subset=['timestamp'], keep='last'). The docstring and test_default_pipeline_cleans_sorts_dedupes_and_resamples ('dup kept last', test_data_registries.py:33) make the contract 'the later row in the file wins'. That is the right rule for exchange data, where a re-download or an appended fetch rewrites a partial candle with its final values. sort_values defaults to quicksort, which is not stable. After sorting, the relative order of equal timestamps is arbitrary, and keep='last' then keeps whichever duplicate happened to land last. The test passes only because its frame has 8 rows, and numpy sorts arrays under 16 elements with a stable insertion sort.

**Failure scenario.** A CSV built from two overlapping downloads (minutes 0..30,000 plus a newer copy of minutes 29,000..43,499): for 510 of the 1,001 duplicated minutes the pipeline keeps the OLD row instead of the re-downloaded one. A sorted file with 87 partial-then-final duplicate candles keeps the partial candle in 18 cases. The kept Close values, and so the windows, targets and direction labels around them, depend on the sort algorithm rather than on the file.

**Evidence (finder, reproduced).** Ran scratchpad/agents/data-pipeline/dedupe_check.py (numpy 1.23.5, pandas 2.0.3, the CI pins): 'overlapping chunks (1001 duplicated minutes): rows 44501, unique 43500, dup-groups kept NOT the file-last row: 510'; 'adjacent duplicates in a sorted file: rows 43587, unique 43500, ... 18'; 'tiny frame: ... 0'. Probe test test_sort_dedupe_keeps_the_file_last_row_of_each_duplicated_timestamp fails on the original code and passes with sort_values('timestamp', kind='stable'). The bundled CSV has 0 duplicates (csv_quality.py), so current results are unaffected.

**Verifier (reproduced): confirmed.** Code: preprocessors.py:36-38 runs df.sort_values('timestamp').drop_duplicates(subset=['timestamp'], keep='last'). The default kind is quicksort, which is not stable. The docstring says 'keep the last row of duplicated timestamps', and tests/registries/test_data_registries.py:33 checks 'dup kept last' on an 8-row frame; numpy sorts arrays that small with insertion sort, which is stable. Run: scratchpad/agents/verify-data-pipeline/v2_dedupe.py (numpy 1.23.5, pandas 2.0.3). Output: 'overlapping chunks, sort_dedupe: rows 44501, unique 43500, dup groups 1001, kept NOT file-last: 510'; 'overlapping chunks, stable sort: ... kept NOT file-last: 0'; 'sorted file with 87 partial-then-final dups, sort_dedupe: ... 13'; 'tiny 8-row frame: ... 0'; through the full default run_preprocessors: 'overlapping minutes that kept the OLD close (1.0): 510 of 1001'. Bundled CSV: 43,500 rows, 0 duplicate timestamps, 0 non-1-minute steps, so current numbers are unaffected.

**Verifier corrections.** The 87-duplicate case depends on where the duplicates fall: my random layout gave 13 of 87 kept wrongly (the finding: 18). The 510 of 1,001 overlapping-chunk result reproduces exactly. The problem is latent: 0 duplicates in the bundled file, and the long Bitcoin_BTCUSDT.csv is not on this machine. The fix (kind='stable') leaves the golden run unchanged. MVP growth point 4 (generality). Land it BEFORE NT-041(7) loads the long-history or multi-download files; it can be batched with the other data-validation work of NT-041. Acceptance as proposed; also require that the bundled-CSV closes are array_equal before and after the change. cpu_cost: instant.

**Backlog check (finder).** Not covered: no BACKLOG, ROADMAP or STATUS item touches preprocessing. REMEDIATION_PLAN only lists sort_dedupe as a registered component (line 157).

**Fix sketch.** preprocessors.py:38: df.sort_values('timestamp', kind='stable').drop_duplicates(subset=['timestamp'], keep='last'). Add a test that is large enough to defeat insertion sort.

**Acceptance (proposed).** (1) Test with >= 30,000 rows and >= 1,000 duplicated timestamps from an overlapping second chunk: every duplicated timestamp keeps its file-last row. (2) tests/registries/test_data_registries.py passes. (3) On the bundled CSV, load_and_prepare_data returns the same 43,500 closes as before (array_equal).

## DATA-4: The data pipeline never checks bar spacing or price sanity: windows and horizon targets silently span missing minutes, and a single zero close inflates the target scale 3.6x

- **Severity:** P2. **Status:** already in the backlog. **Type:** design-risk. **CPU cost:** short. **Placement:** addition to NT-041.

**Description.** validate_ohlcv_frame (loaders.py:32-41) checks only the required columns, that the frame is non-empty, and non-strict ascending order. resample_bars (preprocessors.py:41-52) creates the missing bins and then drops them with dropna(subset=['Close']). make_sequences_with_extended_trends (windowing.py:65-93) counts HORIZON_STEPS in rows, not in time. When a minute range is missing (exchange outage, API hole, a merge of files), nothing warns. A '10-bar' target can then be hours ahead, a 60-bar window can join two market states, and the time-based sequence_anchor_bars and Bars.from_frame mapping go wrong just as silently. The same pipeline feeds Predictor.predict_frame on live data. Non-positive or absurd closes are also accepted: a zero close passes validation and enters targets, windows and the TRAIN-fitted target scaler. The bundled CSV with one close set to 0 (row 20,000, in the train block) loads with no error. The target scaler scale becomes 939 instead of 257.5 (3.65x), which rescales every target, the window normaliser and pred_scale. (An 'inf' close does fail loudly, inside sklearn.)

**Evidence (finder, reproduced).** Ran scratchpad/agents/data-pipeline/input_edge_cases.py: '(1) ... test: 79 sequences span the gap; e.g. anchor 2025-11-07 21:00:00+00:00 : h0 "10 bars" label is 130 min ahead ... total sequences whose window or label crosses the gap: 79 (no warning, no error)'; '(4) ... close=0: loaded without error; scaler mean -1.01 scale 939'. clean_scale.py: 'clean target scaler mean -1.0096 scale 257.5181'. csv_quality.py on the bundled file: 43,500 rows, all diffs 1 min, 0 duplicates, 0 zero-volume bars, 0 OHLC violations.
