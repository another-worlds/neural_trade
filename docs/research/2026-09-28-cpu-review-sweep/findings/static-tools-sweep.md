## TOOL-1: scripts/golden_run.py verify reports 'golden_equal: true' when outputs turn NaN or an inf becomes finite

- **Severity:** P1. **Status:** confirmed. **Type:** bug. **CPU cost:** instant. **Placement:** new item CPU-01.
- **Files:** `scripts/golden_run.py`

**Description.** verify compares each array as diff = np.where(both_nan, 0, |a-b|) and excess = np.nanmax(diff - tol) (golden_run.py:95-98), and an array fails only when excess > 0 (:101). When one side is NaN, |a-b| is NaN and nanmax skips it. When a whole array is NaN, nanmax returns NaN, and NaN > 0 is False. When an inf becomes finite, tol = rtol*inf = inf and inf - inf = NaN, which is also skipped. So verify prints golden_equal true and exits 0 when predictions, the loss history, lambdas or coverage become NaN. The 'by prefix (ok, fail)' line (:105-109) counts the same arrays as failures, because 'excess <= 0' is False for NaN, so the script's output contradicts its own verdict. D-023 makes this exit code the 'no number changed' check for every module move, and the acceptance of NT-026 (8), NT-027 (5), NT-028 (7), NT-036 (2), NT-041 (2), NT-042 (3) and NT-049 (4) relies on it. The repo has no test of golden_run.py.

**Failure scenario.** A module move under NT-027 mis-wires a head so every test prediction is NaN, or the loss history becomes NaN. `python scripts/golden_run.py verify ref.npz` prints 'by prefix (ok, fail): ... pred=0/2', then {"golden_equal": true, "n_fail": 0, "n_missing": 0} and exits 0, and the implementer reports 'golden verify passes'.

**Evidence (finder, reproduced).** Ran agents/static-tools-sweep/repro/golden_nan.py. It loads scripts/golden_run.py, monkeypatches run() with synthetic arrays, runs no training, and saves a reference npz. Exit codes: identical 0; 'one prediction became NaN' 0; 'all predictions NaN' 0 (by-prefix line 'pred=0/2' but {"golden_equal": true, "n_fail": 0}); 'loss history NaN' 0 (by-prefix 'hist=0/1', golden_equal true); 'inf became finite' 0; control 'finite changed by 1.0' 1 (FAIL pred/delta/h0 max|diff|=1). RuntimeWarnings 'All-NaN slice encountered' at golden_run.py:98-99.

**Verifier (reproduced): confirmed.** Code at scripts/golden_run.py:95-101 matches the finding. I wrote my own probe, agents/verify-static-tools-sweep/v_golden.py. It loads the real script, monkeypatches run() with synthetic arrays (no TF, no training), records a reference npz and calls main(['verify', ref]). Exit codes: identical 0; one pred element NaN 0 (by prefix pred=2/0, so no failure is reported anywhere); whole pred array NaN 0 (by prefix pred=1/1 but golden_equal true, n_fail 0); loss history all NaN 0 (hist=0/1, golden_equal true); coverage NaN 0 (coverage=0/1, golden_equal true); reference +inf -> 5.0 exits 0; +inf -> -inf exits 0; +inf -> NaN exits 0. The control, a finite change of 1e-3, exits 1 (golden_equal false). Nothing in docs/DECISIONS.md or the script's docstring says NaN is tolerated. No test covers golden_run.py: grep for 'golden' in tests/ returns nothing.

**Verifier corrections.** (1) The by-prefix line (:105-109) disagrees with the verdict only when a whole array is NaN. A single NaN element, or inf -> finite, +inf -> -inf and +inf -> NaN, shows 'ok' in every line, including the per-array FAIL/ok lines at :104, because 'NaN > 0' is False there too. (2) More items depend on it than the finding lists. 11 backlog items use golden_run.py verify in their acceptance: NT-026, 027, 028, 029, 033, 036, 041, 042, 046, 049 and 054. So do OPERATING_MODEL.md:166, RUNBOOK.md:63 and D-023. (3) worst.sort (:100) sorts tuples that contain NaN keys, so the printed top-12 order is unreliable. The fix should rank by a finite score. Fix and acceptance otherwise as proposed. Growth point 1 (structure). Land BEFORE the first module move of NT-027/NT-026, and before any recording that later items verify against.

**Backlog check (finder).** Not in BACKLOG/ROADMAP/STATUS. The items only use `golden_run.py verify` as an acceptance tool (NT-026, NT-027, NT-028, NT-036, NT-041, NT-042, NT-049). None of them tests the tool itself.

**Fix sketch.** Compare with explicit masks: nan_mismatch = np.isnan(a) != np.isnan(b); inf_mismatch = (np.isinf(a) | np.isinf(b)) & (a != b); finite = np.isfinite(a) & np.isfinite(b); fail when any mismatch, or when |a-b| > atol + rtol*|a| on the finite part. Derive the by-prefix counts from the same boolean. Add tests/test_golden_run.py with the probe's cases (monkeypatched run, no training). Growth point 1 (structure). Land BEFORE the first module move of NT-026/NT-027, because it is their acceptance tool.

**Acceptance (proposed).** (1) tests/test_golden_run.py, with run() monkeypatched: verify exits 1 for one element NaN on one side only, a whole array NaN, a NaN loss history, inf -> finite and +inf -> -inf. It exits 0 for identical arrays, including NaN at identical positions, and for a finite change within atol/rtol. (2) golden_equal is false whenever the by-prefix line reports a failure (same test). (3) Fast suite and ruff pass.

## TOOL-2: Correction to NT-036: the finite-step guard does not skip the step; both Adam optimizers still move every weight

- **Severity:** P2. **Status:** confirmed. **Type:** bug. **CPU cost:** short. **Placement:** addition to NT-036, NT-054.
- **Files:** `src/neural_trade/training/custom_model.py`, `src/neural_trade/training/optim.py`, `src/neural_trade/core/config.py`

**Description.** On a non-finite step, train_step replaces every gradient by zeros (custom_model.py:476-484; the comment at :471-475 says 'Zero the whole update instead') and still calls self.optimizer.apply_gradients and self.indicator_optimizer.apply_gradients (:510-511). Both default to Adam (core/config.py:190-191). With Adam a zero gradient is not a zero update: m <- beta1*m, v <- beta2*v, iterations += 1, and w -= lr*m_hat/(sqrt(v_hat)+eps), about 0.86 x lr per weight in the momentum direction. The indicator logits move at LR x INDICATOR_LR_MULT (5x, optim.py:24-25). Under 'adamw' the weight decay also applies. So a step that nonfinite_grad_steps counts as skipped is a full momentum step, and it also decays the moments. NT-036 acceptance (5) requires only that NaN injection 'leave the weights finite and raise the right counter'. Today's code already passes that, so the defect would survive NT-036 as written. NT-037's health numbers and NT-038's fault injection would then count 'skipped' steps that actually moved the weights. No test covers the guard: tests only assert nonfinite_grad_steps == 0 (tests/test_train_smoke.py:60).

**Failure scenario.** The Adam optimizer from the default Config's registry takes 5 ordinary steps, then gets a NaN gradient guarded exactly as custom_model.py:484 does. Every weight still moves by about -8.6e-4 (lr 1e-3), and optimizer.iterations goes 5 -> 6. The same happens on every non-finite step of a real run, for both optimizers.

**Evidence (finder, reproduced).** Ran agents/static-tools-sweep/repro/adam_zero_grad.py (TF CPU, 2.4 s, no model). Output: 'optimizer: keras.optimizers.optimizer_v2.adam Adam lr 0.001'; 'step_finite: False'; 'weights before: [0.99500006 -1.9950004 0.49500006] after: [0.9941382 -1.9941385 0.4941382] moved by: [-0.00086188 0.00086188 -0.00086185]'; 'iterations: 5 -> 6'.

**Verifier (reproduced): confirmed.** custom_model.py:471-484 zeroes every gradient with tf.where when step_finite is False, and :510-511 still calls both apply_gradients. The comment at :471-475 ('Zero the whole update instead') and the remediation plan's S3 (docs/archive/REMEDIATION_PLAN_2026-09.md:45) both state the intent: no update. My probe, agents/verify-static-tools-sweep/v_adam.py (TF CPU, 2.5 s, no model), builds the real pair with training/optim.build_optimizers(Config(...)). It takes 5 steps on a 3-weight variable, then applies a NaN gradient guarded exactly as :484 does. adam main (optimizer_v2.Adam, lr 0.001): step_finite False, moved [-8.617e-4, +8.618e-4, -8.615e-4], iterations 5->6. adam indicator (lr 0.005): moved about 4.30e-3 per weight, iterations 5->6. adamw main and indicator (optimizer_experimental.AdamW): about 8.66e-4 and 4.32e-3, iterations 5->6. The only guard assertion in the tests is nonfinite_grad_steps == 0 (tests/test_train_smoke.py:60). NT-036 acceptance (5) checks only 'weights finite', so today's code would pass it.

**Verifier corrections.** (1) Today the defect rarely fires. NT-036's own 'why' says the loss masks non-finite terms, so only non-finite gradients trip the guard, and reference runs log 0 such steps. NT-036 (2) strict mode will make the guard fire on every non-finite loss term. So the defect becomes live exactly when NT-036 lands, and in NT-038 fault injection. That strengthens 'Correction to NT-036'. (2) NT-054 (2) ('fused finite guards', same train_step code) touches the same lines, so the fix must be coordinated with it. (3) The skip must also work for AdamW, which in TF 2.10 is optimizer_experimental with a different apply path from optimizer_v2 Adam. Test both registry optimizers. Fix: create the slots before the first step, then skip both apply_gradients with tf.__internal__.smart_cond / tf.cond on step_finite (the pattern of Keras LossScaleOptimizer). NT-036 (5) should read 'weights, optimizer slots (m, v) and iterations of both optimizers unchanged by a non-finite step'. Growth point 3 (gradient stability). Land DURING NT-036, before NT-038, and compare the D-018 speed. Acceptance as proposed, plus the AdamW case.

**Backlog check (finder).** NT-036 (why and acceptance (5)) and NT-037 describe the guard as counting non-finite steps. Neither says the zeroed step still applies an Adam update, and NT-036 (5) accepts 'weights finite', which the defect already satisfies. Hence 'Correction to NT-036'.

**Fix sketch.** Build both optimizers' slots once before the first step, then run each apply_gradients inside tf.cond(step_finite, apply, tf.no_op), the pattern LossScaleOptimizer uses to skip non-finite steps. Keep the counter. Change NT-036 acceptance (5) from 'weights finite' to 'weights, optimizer slots and iterations of both optimizers unchanged'. Growth point 3 (gradient stability). Land DURING NT-036, and check D-018 per-step speed.

**Acceptance (proposed).** (1) TF test: a train_step on a tiny model with one injected NaN gradient leaves every trainable variable, every Adam slot (m, v) and optimizer.iterations of both optimizers bit-identical, and nonfinite_grad_steps rises by 1. (2) A finite batch after it gives the same weights as a run that never saw the NaN batch (test). (3) The 1-epoch CPU smoke's sec_per_step is not slower (D-018). (4) scripts/golden_run.py verify passes.

## TOOL-6: Backtest tp_sl_on='close' fills a stop that is seen only at the close at the stop level, a better price than any available by then

- **Severity:** P3 (reported P2). **Status:** confirmed. **Type:** bug. **CPU cost:** instant. **Placement:** new item CPU-23.
- **Files:** `src/neural_trade/strategy/backtest.py`, `src/neural_trade/notebook/backtest_ui.py`, `tests/test_backtest.py`

**Description.** In 'close' mode the trigger uses the close (backtest.py:222: hi_px = lo_px = c). The fill is still min(sl, open) for a long stop and max(tp, open) for a long take-profit (:234, :237), which are prices from the intrabar path the mode claims not to see. When the close has passed the stop, the stop fills at the stop level, which is optimistic by the close-to-stop distance. A take-profit fills at the TP level below the close, which is pessimistic. The asymmetry favours stop-heavy strategies. The notebook widget offers the mode (backtest_ui.py:506), and COST_FIELDS carries it into saved settings (:24). tests/test_backtest.py:102-107 checks only the trigger, not the fill price. The leaderboard ranks by net Sharpe from this engine, and the new engine inherits it.
