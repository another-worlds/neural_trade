## CORE-1: The learned-period ceiling MOMENTUM_CLIP_MAX stays at 60 bars when LOOKBACK changes through override(), --set, notebook OVERRIDES or configs/default.yaml. The ceiling equals the window only when a Config is constructed.

- **Severity:** P1. **Status:** confirmed. **Type:** bug. **CPU cost:** instant. **Placement:** new item CPU-06.
- **Files:** `src/neural_trade/core/config.py`, `configs/default.yaml`, `src/neural_trade/training/custom_model.py`, `tests/test_config.py`, `docs/RUNBOOK.md`, `docs/research/2026-09-28-window-free/README.md`

**Description.** Config.__post_init__ (config.py:229-230) sets MOMENTUM_CLIP_MAX = LOOKBACK once and stores the value. override() and copy() (config.py:314-331) never recompute it. configs/default.yaml:84 also fixes it explicitly at `MOMENTUM_CLIP_MAX: 60`, and every saved run's config.yaml writes 60.0. After every optimizer step the trainer clips the learned periods to cfg.MOMENTUM_CLIP_MAX (custom_model.py:516-519, which calls learnable_indicators.clip_learned_periods). Three sources assume the ceiling follows the window: the field doc ('period ceiling; None -> LOOKBACK', config.py:150), the documented CLI path (`--config configs/default.yaml --set ...`, RUNBOOK.md:90) and the window research ('that ceiling is the window itself (config.py:150, :229-230)', research README.md:20 and :217, the input to NT-053). tests/test_config.py:84-86 checks only construction (Config(LOOKBACK=32)), never an override.

**Failure scenario.** `neural-trade train --config configs/default.yaml --set LOOKBACK=120`, or notebook 01 with OVERRIDES={'LOOKBACK': 120}, or Config().override(LOOKBACK=120) trains with the ceiling at 60. The slow MACD period, which already drifts to 60 in 3 of 7 local runs, is then clamped at half the window. With LOOKBACK=30, or NT-041's 60-minute window at 5-minute bars (12 bars), the ceiling stays at 60 bars: learned periods can reach 5x the window, where the cold-started EWMA is mostly the window's first close. There is no error and no warning, and the run's config.yaml shows the stale ceiling as if it had been chosen.

**Evidence (finder, reproduced).** Ran <scratch>/agents/core-config-cli/probe_config.py (section 2). Output: `Config().override(LOOKBACK=30) -> MOMENTUM_CLIP_MAX=60.0, momentum_clip_max=60.0`; `Config().override(LOOKBACK=120) -> 60.0`; `default.yaml.override(LOOKBACK=30) -> 60.0`; `default.yaml.override(LOOKBACK=120) -> 60.0`; but `Config(LOOKBACK=120).MOMENTUM_CLIP_MAX = 120`. Candidate fix, tested in a scratch copy (agents/core-config-cli/wt): the stored value stays None, custom_model.py:517 reads cfg.momentum_clip_max, and default.yaml says `MOMENTUM_CLIP_MAX: null`. With the new assertions override(LOOKBACK=120) -> 120 and from_yaml(default.yaml).override(LOOKBACK=120) -> 120, `pytest tests/test_config.py tests/test_physics_terms_bounded.py::test_clip_learned_periods_never_saturates_the_logit tests/test_viz_indicators.py -n 2` gave 51 passed in 7.45 s. The default stays at 60, so the golden run is unaffected.

**Verifier (reproduced): confirmed.** Code at ffb1b67 (src/ is identical to 7785ec9): config.py:229-230 sets MOMENTUM_CLIP_MAX = LOOKBACK only in __post_init__. override() (:314-327) and copy() (:329-331) never recompute it. default.yaml:84 fixes it at 60. custom_model.py:516-519 clips with cfg.MOMENTUM_CLIP_MAX. I ran agents/verify-core-config-cli/v_core1.py. Output: `Config().override(LOOKBACK=30) -> MOMENTUM_CLIP_MAX=60.0`, `Config().override(LOOKBACK=120) -> 60.0`, `from_yaml(default).override(LOOKBACK=30|120) -> 60.0`, `Config(LOOKBACK=120).MOMENTUM_CLIP_MAX = 120`. The CLI path gives the same: `cli _load_config(None, LOOKBACK=120) -> 60` and `cli _load_config(default.yaml, LOOKBACK=120) -> 60.0`. Notebooks 01-05 use `Config.from_yaml(CONFIG_PATH).override(**OVERRIDES)` (build.py:57, :110). Train-step clip, tiny TF op, no training: I set every learned period to 100 and called layer.clip_learned_periods(cfg.MOMENTUM_CLIP_MIN, cfg.MOMENTUM_CLIP_MAX), the same call as custom_model.py:516-519. Output: `Config(LOOKBACK=120): ... -> 100.0..100.0` and `Config().override(LOOKBACK=120): ... -> 60.0..60.0`. Extra sub-case: validate uses the stale value too. Config(LOOKBACK=2) is refused ('need 0 < MOMENTUM_CLIP_MIN < MOMENTUM_CLIP_MAX'), but Config().override(LOOKBACK=2) is accepted with the ceiling at 60. No backlog item covers this. NT-053 and D-032 plan to remove the ceiling only after the owner approves a plan.

**Verifier corrections.** Facts: the lines and the default-60 behaviour are as reported. No cited number is affected, because every cited run uses LOOKBACK=60. The damage starts with the first non-default window (NT-041, or a sweep over LOOKBACK in NT-030). P1 is kept because the documented override paths then silently build a different model. The research README (:20, :217) is right at LOOKBACK=60 and wrong only as a general statement. **Fix sketch.** Store MOMENTUM_CLIP_MAX only when it is explicitly set (keep None) and resolve it where it is used through Config.momentum_clip_max (config.py:296): at custom_model.py:517, in validate (config.py:286) and in indicator_evolution.py:207, which already falls back to LOOKBACK. **Acceptance (proposed).** (1) Config().override(LOOKBACK=120).momentum_clip_max == 120 and Config.from_yaml('configs/default.yaml').override(LOOKBACK=30).momentum_clip_max == 30 (test). ## CORE-2: Evidence for NT-026 / NT-030 / NT-031: today's config_hash cannot identify a configuration. Seed, fold, paths, doc comments and dict key order all change it; it is 32 bits; and run ids with one-second resolution collide.

- **Severity:** P2 (reported P1). **Status:** confirmed. **Type:** design-risk. **CPU cost:** short. **Placement:** addition to NT-026, NT-031.
- **Files:** `src/neural_trade/experiments/run_context.py`, `src/neural_trade/core/config.py`, `src/neural_trade/utils/env.py`

**Description.** config_hash (run_context.py:31-32) is sha256(config.to_yaml())[:8]. to_yaml (config.py:348-370) emits group header comments and each field's doc string as a comment (config.py:365-366), with nested dicts in insertion order (sort_keys=False). RunContext.create writes SEED into the config before hashing (run_context.py:47-50), and FOLD_INDEX, CSV_PATH and the path fields are all part of the text. NT-026 (2) puts 'config hash' in the index, NT-030 (2) resumes Optuna studies, and NT-031 (1) needs 'one row per configuration' averaged over dev folds and seeds. None of these can use today's hash. The run id is stamp(seconds)-sha-hash (run_context.py:49-52, mkdir exist_ok=False). git_sha marks a tree dirty only for tracked changes (utils/env.py:21, `git diff --quiet HEAD`), so a run that uses an untracked new module under src/ is labelled with a clean commit.

**Failure scenario.** The same configuration run with seeds 0/1/2 on folds -3/-2 gets 6 different hashes, so a leaderboard grouped by hash shows 6 rows. NT-029 adds docs to 26 fields, and with today's hash that changes every configuration's hash: a sweep interrupted before NT-029 and resumed after it matches no finished cell and re-runs everything, or it double-counts rows. Two Optuna trials in one --parallel batch that sample the same categorical point, with the same seed, start in the same second: the second one crashes with FileExistsError.

**Evidence (finder, reproduced).** Ran agents/core-config-cli/probe_config.py (section 5). All values are config_hash(cfg.copy()), which is what RunContext uses. SEED 42 vs 7: 6f1d21e8 vs 90888815. CSV_PATH 'binance...csv' vs './binance...csv': 6f1d21e8 vs 7bda8d38. MODEL_PATH runs/ci/weights.h5 (as in configs/ci.yaml): c5fc1238. Doc-only edit of the EPOCHS field's metadata: 6f1d21e8 -> ad7207d3. Without copy(), config_hash(Config()) = 28905c3b vs config_hash(Config.from_yaml('configs/default.yaml')) = 6f1d21e8, because int 60 vs float 60.0 in MOMENTUM_CLIP_MAX. A one-liner created RunContext.create(Config(LR=3e-4)) twice: `first run 20260928T000341Z-1a2457a-34afd9c8 | second identical run in the same second -> FileExistsError`. From CORE-3's probe: a 1-epoch run without lambda calibration and a default 20-epoch calibrated run share hash 6f1d21e8. 8 hex characters are 32 bits, so the birthday collision chance is about 1.2% at 10k configurations.

**Verifier (reproduced): confirmed.** run_context.py:31-32 hashes config.to_yaml()[:8]. to_yaml writes the doc comments (config.py:365-366) and keeps key order (sort_keys=False). RunContext.create sets SEED before hashing (:47-50) and calls mkdir(exist_ok=False) (:52). I ran agents/verify-core-config-cli/v_core2.py; all values are config_hash(cfg.copy()). base 6f1d21e8. SEED 7: 90888815. FOLD_INDEX -2: be1ecb2d. MACD dicts with reordered keys (== True): b4ebd0e5. LAYERS reordered (== True): 8abe0102. './'+CSV_PATH: 7bda8d38. The run id reads 'ffb1b67' with no -dirty although the worktree has untracked ci_runs/ and coverage.json: utils/env.py:21 `git diff --quiet HEAD` ignores untracked files. **Verifier corrections.** Severity lowered from P1 to P2. Today the hash is only a display suffix in run ids, and no number depends on it. Its value is as design input for NT-026 (2) and NT-031 (1), which must define their own configuration key. The MACD-reorder digest depends on the permutation: I got b4ebd0e5, the finder b88691b0. The claim that resume after NT-029 re-runs everything holds only if the implementer keys resume or grouping on today's hash. NT-026 (2) already names a cell key for resume. The real risks are leaderboard grouping by hash (NT-031 (1)) and duplicate cells. The collision needs the same config, seed and fold within one second, e.g. a duplicate Optuna trial in a --parallel batch. NT-026 (3) forbids overwriting, so the runner needs a uniqueness suffix, not exist_ok. The rest of the fix sketch and acceptance stand. Growth points 1 and 2: during NT-026, before NT-029 adds its docs.

**Backlog check (finder).** NT-026 lists 'config hash' as an index column but does not define it. NT-030 and NT-031 depend on grouping by configuration. No item addresses canonicalisation, collisions or the dirty flag. This gives NT-026's implementer the hidden sub-cases and failing probes.

**Fix sketch.** Add one canonical fingerprint function, in core/config.py or experiments/. It hashes json.dumps(sort_keys=True) of to_dict() with types normalised through from_dict. Resume matches on (scenario, cell key) and reports a changed fingerprint as a conflict instead of treating it as a new cell. Run ids get a uniqueness suffix (the cell key or a counter). The dirty flag uses `git status --porcelain -- src scripts`. Growth points 1 and 2: land during NT-026, before NT-029's doc additions, which would otherwise change every hash.

**Acceptance (proposed).** (1) One configuration with SEED 0/1/2 and FOLD_INDEX -3/-2/-1 has one fingerprint, and two configs that differ in one tunable value have different fingerprints (test). (2) The fingerprint does not change for a field doc edit, for reordered keys in MACD_SETTINGS / LAYERS / LOSS_WEIGHT_SCHEDULE, for './x.csv' vs 'x.csv' naming the same file, or for Config() vs Config.from_yaml('configs/default.yaml') (test). (3) Two RunContexts of an identical config created within one second get distinct run directories (test). (4) The index stores the full digest, and a resumed scenario after a doc-only commit re-runs no finished cell (test on the tiny CPU scenario). (5) A run created with an untracked .py file under src/ is marked dirty (test in a temporary git repo).

## CORE-10: Config.override changes the Config in place and is not atomic, and train_and_evaluate writes config_overrides and csv_path into the caller's Config

- **Severity:** P2. **Status:** confirmed. **Type:** design-risk. **CPU cost:** instant. **Placement:** new item CPU-17.

**Description.** override() assigns every value with setattr and only then calls validate (config.py:323-326). A refused override leaves the object mutated and invalid.
