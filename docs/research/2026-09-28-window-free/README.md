# Research: removing the fixed input window (2026-09-28)

Asked by the owner on 2026-09-28 ([indicator Q&A](../../qa/2026-09-28-indicators.md), Round B): "I want a
massive optimization of this process: currently the 'window' is a huge limiting factor in the
training. I think we can get rid off it completely. Research this."

Method: five parallel investigations (impact map of the window in the code, compute profile with CPU
benchmarks, TF 2.10 design options, prior art, statistical consequences), a synthesis, and an
adversarial review that re-ran parts of the prototypes. **Every GPU number below is an estimate;
the measurements are CPU-only** (the GPU is shared; no GPU job was run). The prototype scripts and
their JSON outputs are in [prototypes/](prototypes/) (they were written in a session scratchpad; the
paths inside them point there). The owner's decisions on this research are recorded in
[docs/qa/2026-09-28-indicators.md](../../qa/2026-09-28-indicators.md) and DECISIONS.

The adversarial review ("Challenge" at the end) found must-fix problems in the proposed A/B
specifications and some estimates; **its corrections take precedence** over the synthesis where they
conflict.

## Answer (synthesis)
Yes, the window can go, but in stages. The evidence says its main cost today falls on the indicators, not on GPU time. Measured: the learned slow MACD period reaches the 60-bar ceiling (60.0) in 3 of 7 local runs and 56.7 to 60 in all four 20-epoch runs, and that ceiling is the window itself (config.py:150, :229-230). Every EWMA restarts at the window's first bar: at period 60 the error at the last bar is 15% of the feature's size, and 39% mid-window. The windowed EWMA's memory grows with the square of the window, and its compute grows with the number of indicators, so the planned 14-family OHLCV catalogue, or periods longer than an hour, do not fit the current design. The GPU step, however, is limited by the number of kernel launches, not by arithmetic (about 1% of the GPU's compute is used, an estimate). So computing each bar 60 times costs less than it seems, and the window is not what makes a run take 5 minutes. Stage 1 replaces the per-window indicators with one causal pass over the whole series, while the network still reads the last 60 bars of those indicators. The pass is a chunked recurrence that runs in TF 2.10 with no new packages; on the CPU it matched a float64 reference to about 1e-5 over 30k bars. This removes the ceiling, the cold start and the quadratic memory, and it keeps today's network, losses, calibration and baselines unchanged. It is also the engine the new indicator families need. The GPU cost per step should stay about the same (an estimate, to be measured). Stage 2 removes the window from the network as well: a causal model that predicts at every bar of long chunks. On the CPU a sketch of it handled 12-25x more predictions per second (measured). On the GPU the estimate is 9-17x faster per epoch and 3.5-4x faster per whole run as the pipeline stands, but only if the model learns as much per epoch from fewer, larger updates; if it needs as many updates as today, the gain is about zero. So a cheap probe runs first (batch 1024 against 256, about 1 GPU-hour). Stage 2 also needs a new causal architecture, per-position versions of the batch-level physics terms, and a pre-registered paired A/B. Today's model stays the default and the golden-run baseline until each A/B says otherwise. The main risks: future-bar leakage (measured: four of today's layers read later bars when run over a chunk); the purge rule for indicators with unbounded memory; float32 precision on long series (avoided by working in price increments and short chunks); and per-window adaptive periods becoming per-bar. Separately from the window, the fixed costs of each run (about 59 of 296 s: tracing, epoch-end time, setup) and the launch count are cheap targets that the 5-minute quick sweeps need anyway.

## Risks and mitigations
- All GPU numbers for the new designs are estimates. CPU ratios (about 1,000x on the indicator stage, 12-25x throughput for the per-bar sketch) do not transfer to a launch-bound GPU. -> Step 0b measures the kernels and the batch-size probe on the GPU before anything is built. Each later gate uses measured GPU numbers (D-018), never the CPU ratios.
- Update-bound learning: the per-bar model does about 8-16x fewer updates per epoch. If it needs as many updates as today, its speed gain is about zero. -> The batch-size probe (0b) classifies the model before B is built. A/B-2's primary is fit wall-clock to a stopping rule, not time per epoch. The LR is re-tuned in at most 3 variants on dev folds.
- Future-bar leakage. Measured on CPU: the Bi-GRU (gru_attention.py:62), 'same'-padded Conv1D (:78-80), unmasked attention (:67, :92) and global pooling (:49, :102) change past outputs when later bars change. Harmless inside a window, they leak when a chunk emits one prediction per bar. -> A2 keeps the network's window, so only the indicator kernel must be causal (step 1 test). B must pass gates T1-T6 before any GPU time, plus assert_no_lookahead.
- Purge rule. With unbounded indicator memory, D-005's literal invariant (no training-label bar is an evaluation input, splits.py:26-37) holds only with a state reset and a burn-in inside each gap. That costs about 4.5% of a fold at a 1-hour ceiling, about 18% at 4 hours and about 51% at 1 day (estimate for a 7+3-day fold). -> An owner question with a recommendation: the label-overlap rule (gap >= max(H) plus an embargo), because memory of earlier bars is genuinely past information, available live. A new DECISIONS entry and a split test record the rule. 80 bars are kept during the A/Bs so the anchors stay identical. Config validation refuses ceilings whose burn-in exceeds 10% of the training block.
- Float32 precision on long series. Measured: global log-cumsum decays err by up to 0.86% at 43k bars; a recurrence on raw price levels is about 80x less precise than the increment form; EMA(x^2)-EMA(x)^2 on raw prices had a 22% median relative error (synthetic data). -> Increment form (d_t = (1-a_t)(d_{t-1} - dx_t)) and chunk-local cumsums (C=64-128) only. Precision tests at 30k and 43k bars. The Bollinger variance is computed as EWMA(d^2). FFT and tf.scan are ruled out (measured error and speed).
- Non-finite contamination. One NaN or Inf bar makes every earlier output of the matrix EWMA and of causal-masked attention non-finite (measured, 0 x NaN). Series mode would lose a whole block, where the window model loses only the windows that contain the bar. -> A finite-input data contract checked at load (with NT-041's gap policy), and the engine refuses non-finite input with an error (step 1 test).
- Semantics change: per-window adaptive periods (D-031, 'reported as a range') become a per-bar, time-varying alpha. 'The period applied to a window', the frozen twin (NT-033) and the D-027 view change meaning. -> An owner question with a recommendation (per-bar alpha, 5-95% range over bars, D-031's off switch kept). Redefine the frozen twin and the view text before the leaderboard compares them.
- Physics and batch-statistic loss terms (T-perp, HD, IFE, soft-ECE, vol loss, vacuum overflow) and the lambda calibration change meaning under chunked batches in B. Two reductions (VacuumSaturationNoise axis 0, vacuum_overflow Lambda axis=1) would run without error on [B,T,D] and compute the wrong statistic. The v1 ablation (D-003) does not transfer. -> A2 leaves the losses untouched. In B: compute these terms on a strided subsample of positions; add axis tests on [B,T,D]; run lambda calibration per arm; re-target NT-006 on the adopted architecture (the owner is asked).
- Pre-registered baselines (logreg_lags with lags up to 59 and window volatility, baselines.py:24-41) and the D-008 realized_vol intervals are defined on the 60-bar window. -> A2 still passes the raw close window to them, so they are unchanged. In B they are computed from the close series with the same spans (lags 1-59, RV over 60 bars), with equality tests against the window versions.
- Evidence continuity: 21% of today's parameters have LOOKBACK-shaped weights (measured: 62,036 of 296,591), so saved bundles and cited runs cannot load into a window-free model. -> Coexistence: the window path stays registered and stays the default until an A/B adopts the replacement, and the golden run keeps guarding it (D-002, D-029).
- Truncated-BPTT bias in B. A stop-gradient at chunk starts biases learned long periods towards short ones (Tallec and Ollivier 2017). -> In A2 the gradient flows through the whole series. In B: chunks much longer than the longest period, or a gradient through the burn-in. Test T5 checks offset invariance.
- Curse of memory: long-period logits become the most sensitive parameters once the 60-bar cap is gone, and INDICATOR_LR_MULT / INDICATOR_GRAD_MULT = 5 amplify them (LRU literature lowers the LR on recurrent parameters). -> A named case in the stability harness (NT-038). If the harness flags it, a log-timescale parametrisation or a lower multiplier for long periods. Config validation refuses regions known to fail (D-026).
- Underpowered guard-rails. Measured paired SDs: h1 AUC 0.021, log CRPS 0.0087, net Sharpe 20 annualised units. With 6 pairs only coarse margins can be shown, and the net Sharpe guard-rail catches only large regressions. -> Margins are stated before the run; INCONCLUSIVE is accepted as an outcome; 12 pairs are used after NT-041 (3 held-out folds x 4 seeds).
- Timing contamination on the shared GPU (v1: per-epoch time up to 5x the median). -> The RUNBOOK GPU-free check before each run; an epoch above 1.5x its run's median flags contention and the run is re-timed; runs interleaved A,B,B,A.
- Amdahl: about 59 s of the ~296 s run is fixed or outside the epochs, so faster epochs alone cannot meet the 5-minute quick-sweep goal. -> Parallel item P (launches, tracing, epoch-end work); the 7-day training block (NT-041).

- [literature] [3 every-step training] 'Forking sequences' (introduced by MQ-RNN in 2017, formalised in TMLR 2026): encode the whole series once and emit the full multi-horizon forecast at every time step, instead of sampling windows. The paper's encoder cost table gives RNN/CNN/MLP O(T^2) -> O(T), Transformer O(T^3) -> O(T^2), S4 O(T^2 log T) -> O(T log T).
